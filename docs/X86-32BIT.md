# 32-bit x86 (PE32) processes — design notes (v1.20)

The emulator runs **PE32 executables as 32-bit processes** on the same interpreter that runs x86-64 code.
Nothing is translated or recompiled: the CPU core gains an *IA-32 compatibility mode* and the Win32
personality gains 32-bit calling conventions, 32-bit structure layouts and x86 structured exception handling.

## CPU: IA-32 compatibility mode (`emu/x64/cpu.c`, `emu.h`)

* `Cpu.mode32 = 1` → default operand size 32, address size 32 (`0x67` → 16), stack pointer is `esp`,
  no REX prefixes (`0x40–0x4F` are `inc/dec reg`), `push/pop/call/ret/iret` move 4 bytes, `pushad/popad`,
  `enter/leave`, `aaa/aad/aam/aas/daa/das`, `bound`; `fs:` reads go to the 32-bit TEB,
  `gs:` to the TEB too (as on WOW64).
* The decode cache keys on `(rip, mode)`; the x64 fast paths stay untouched.
* The same x87/SSE units serve both modes (`fld tbyte`, `fistp`, SSE2 double math).

## Loader (`emu/x64/pe.c`)

* PE32 (`magic 0x10b`) exes and DLLs are mapped at their preferred base or relocated below 2 GB
  (`IMAGE_REL_BASED_HIGHLOW`); imports by name and ordinal; `DllMain`, TLS directory, TLS callbacks,
  export forwarders — the same code as PE32+ with 4-byte pointer thunks.
* Memory map of a 32-bit process: exe `0x400000`, stack `0x10000000–0x10800000` (8 MB), heap from
  `0x20000000` (16 MB regions, capped at `0x48000000`), `VirtualAlloc` reservations `0x48000000–0x60000000`,
  DLLs from `0x60000000`, framebuffer `0x70000000`, shim slots and the TEB/PEB below 2 GB.
  Fake module handles (`GetModuleHandle("kernel32")` …) are `0x7f000000 + slot<<12`.
* Mixed images are rejected honestly: a 32-bit process cannot load an x86-64 DLL and vice versa.

## Calling conventions (`emu/x64/win32_x86.inc`, `stdcall32.inc`, `emu/tools/stdcall32.py`)

Every shim is written once, against `ARG(n)`/`RET(v)`. In a 32-bit process the shim slot pops the return
address, reads the arguments from the stack, runs the x64 shim body and then performs **stdcall cleanup**:
the number of bytes to pop comes from `stdcall32.inc`, generated from 53 Wine `.spec` files (1256 APIs);
cdecl CRT functions clean nothing. 64-bit arguments (`LARGE_INTEGER`, `double`, `__int64`) occupy two
slots and are re-joined by the marshaller; `double` results are returned in `ST(0)`, 64-bit results in
`edx:eax`; `__thiscall` callbacks (copy constructors, destructors) get `ecx`.

Guest callbacks (`guest_call`) push a 32-bit frame: arguments right to left, the continuation slot as the
return address; the continuation restores `esp`, so stdcall and cdecl callees both work.

## 32-bit layouts

`PSZ_OF(c)` / `rdp` / `wrp` make pointer-sized fields follow the process bitness. Structures with their
own 32-bit layout: TEB32 (`ExceptionList@0`, `StackBase@4`, `Self@0x18`, `Pid@0x20`, `Tid@0x24`,
`Peb@0x30`, `LastError@0x34`, `TlsSlots@0xE10`), PEB32, `RTL_USER_PROCESS_PARAMETERS32`, `STARTUPINFO`
(68 B), `SYSTEM_INFO` (36 B), `MEMORY_BASIC_INFORMATION` (28 B), `OVERLAPPED` (Internal@0, InternalHigh@4,
Offset@8, hEvent@16), `IO_STATUS_BLOCK`, `CRITICAL_SECTION`/SRW/condition variables/`INIT_ONCE`,
`PROCESS_BASIC_INFORMATION`, `WSABUF {len@0, buf@4}`, `fd_set` (array at +4), `WSAPOLLFD` (8 B),
`addrinfo` (32 B), `MSG` (28 B), `WNDCLASS(EX)`, `CREATESTRUCT`, `PAINTSTRUCT`, `BITMAP` (24 B),
`LOGBRUSH` (12 B), msvcrt `FILE` (32 B stride), `_JUMP_BUFFER` (`Ebp Ebx Edi Esi Esp Eip Registration TryLevel Cookie`).

## x86 structured exception handling (`emu/x64/seh32.inc`)

x86 has no unwind tables: each function with handlers links an `EXCEPTION_REGISTRATION {next, handler}`
into the chain at `fs:[0]`. The emulator implements the kernel's part of the protocol, with every handler,
filter and funclet executed as a guest callback through the continuation stack:

| piece | behaviour |
|---|---|
| `RaiseException`, hardware faults (AV, `idiv` by zero, `ud2`) | `EXCEPTION_RECORD` (80 B) + `CONTEXT` (0x2CC: `Edi@0x9C … Eip@0xB8, Esp@0xC4`, FXSAVE area) on the faulting thread's stack; vectored handlers first; then every frame's handler `cdecl handler(rec, frame, ctx, dispatcher)` from the chain head up |
| `ExceptionContinueExecution` | the (possibly modified) `CONTEXT` is loaded — `Eip`/`Esp`/`Eax` fix-ups work |
| `ExceptionContinueSearch` | next frame; past the end of the chain → `SetUnhandledExceptionFilter` callback → honest "unhandled exception" report |
| `RtlUnwind(target, ip, rec, retval)` | walks from the head to `target`, calls each handler with `EXCEPTION_UNWINDING` (`EXIT_UNWIND` when target is 0), unlinks it, then returns to the caller with `eax = retval` (or jumps to `ip`) — the caller's registers come back from the context captured at entry, as on Windows |
| `_except_handler3`, `_except_handler4_common` | MSVC `__try/__except/__finally`: scope table `{prevLevel, filter, handler}` (EH4: cookie-XORed pointer, 16-byte header, `TRYLEVEL_NONE = -2`), filters run with `ebp` = owner's frame and `[ebp-0x14]` = `EXCEPTION_POINTERS`, `EXCEPTION_EXECUTE_HANDLER` → global unwind to the frame → local unwind (`__finally` funclets) → jump into the `__except` block with `esp` from `[ebp-0x18]`; `EXCEPTION_CONTINUE_EXECUTION` → resume |
| `_local_unwind2/4`, `_global_unwind2` | the same machinery, called directly by compiled code for `__leave`/`return` out of `__try` |
| `__CxxFrameHandler` (`__CxxFrameHandler2/3` alias) | MSVC C++ EH on x86: the per-function thunk `mov eax, FuncInfo; jmp __CxxFrameHandler` lands in the shim with `FuncInfo` in `eax` (`magic 0x19930520–22`, `maxState`, `pUnwindMap`, `nTryBlocks`, `pTryBlockMap`, `EHFlags`); the current state is `frame->trylevel` (`[ebp-4]`); catch clauses match by `type_info` name with const/volatile/reference adjectives; the exception object is copied into the catch variable (`dispCatchObj` relative to `ebp`: pointer for references, `memcpy` for simple types, `__thiscall` copy constructor otherwise, virtual-base `this` adjustment); global unwind → cleanup actions from the unwind map → catch funclet on the owner's `ebp` → its return value is the continuation address; the exception object's destructor runs after the block; `throw;` rethrows the exception being handled; `FUNC_DESCR_SYNCHRONOUS` frames ignore SEH exceptions, `catch(...)` still catches them |
| `longjmp` | `Registration` ≠ chain head → global unwind to the `setjmp` frame first; `_setjmp`/`_setjmp3`/`_setjmpex` store the x86 `_JUMP_BUFFER` |

The gcc/clang ABI (mingw builds: DWARF/SjLj unwinding inside libgcc) needs nothing from the OS and works as before.

## Tests (`emu/tests/run.sh` section [18], CI)

`hello32.exe`, `seh32.exe` (9 checks), `cxxexc32.exe`, `pthreads32.exe`, `netloop32.exe`, `NebulaStrike32.exe`
(frames) and the **official 32-bit `7za.exe` 25.01**: help, `a -mx5` (LZMA2 with worker threads), `x`, bit-exact
round trip, and the error path that goes through `_CxxThrowException` → `__CxxFrameHandler` → `catch` and prints
`System ERROR: …`. In the browser: e2e scenarios `hello32.exe`, `seh32.exe`, `NebulaStrike32.exe`.

## Honest limits

* No 16-bit code, no real-mode/V86, no LDT/segment descriptors (only `fs`/`gs` bases).
* `IsWow64Process` reports "not WOW64" (there is no 64-bit kernel underneath); `Wow64*` APIs are absent.
* The runtime packs (VC++ redistributable, .NET, DirectX) are **x64 only** so far — a 32-bit program that
  imports the real x86 `msvcp140.dll` or `d3dx9_43.dll` stops at the import with the DLL name. x86 packs come
  with the next releases.
* The dialog manager (`CreateDialogParam`, `DialogBoxParam`, `GetDlgItem`, standard controls, menus, common
  controls) is not implemented in either bitness yet; installers (7-Zip's own `7z2501.exe`, NSIS, Inno Setup)
  now load, initialise the CRT and stop at `CreateDialogParamW` instead of being rejected up front. That is
  the next step (v1.21).
* `%Lf` of an 80-bit `long double` is printed as a double — exactly what msvcrt/UCRT do on Windows.
